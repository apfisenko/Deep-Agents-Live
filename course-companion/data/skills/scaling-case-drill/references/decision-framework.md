# Decision framework — как выбирать швы и протоколы

> Источник истины ментора по части «как выбирать». Самодостаточно. Содержание:
> 1. Гейт: а нужно ли выходить из одного процесса (строится ПЕРВЫМ)
> 2. Разложение по осям (диагностический каркас)

> 4. Пары-соседи
> 5. Композиции и расстановка по типовым продуктам

## 1. Гейт: а нужно ли выходить из одного процесса (строится ПЕРВЫМ)

**Дефолт — один процесс.** Он дёшев, отлаживаем и консистентен: состояние в памяти, ошибки видны
сразу, стектрейс сквозной, сетевых границ и координации нет. Всё распределённое — **обмен этой
простоты на конкретные новые возможности**, и обмен всегда платный. Если плюсы распределённости
не нужны — её минусы получишь всё равно, целиком.

Выход из процесса заводится под **конкретный симптом** из четырёх:

1. **Долгая операция блокирует диалог**, а пользователю в это время есть чем заняться.
2. Часть системы живёт **чужим жизненным циклом** — другая команда, свои релизы.
3. Появились **внешние потребители** — чужой код или чужой агент должен уметь позвать твоего.
4. Интерфейс **перерос плоский текст**.

Нет симптома — нет задачи масштабирования; «остаёмся в одном процессе» — здравый инженерный
выбор, а не технический долг.

**Цена, которую участник обязан назвать:** при пересечении сетевой границы разом возникают все
«восемь заблуждений распределённых вычислений» (сеть надёжна, задержка нулевая, полоса бесконечна,
сеть безопасна…) — целый класс проблем, которых в монолите не могло быть даже в теории. Плюс
конкретика: stateless-инстансы + внешний стор = новая точка отказа; восстановление после падения
воркера — минуты, не миллисекунды; multi-tenancy и авторизация — новые слои; сам способ передачи
работы между частями системы легко стоит десятки процентов лишних вызовов и токенов на той же
задаче.

**Анти-паттерн — лечить несуществующую болезнь.** Скромный внутренний ассистент одной команды с
операциями на секунды → никакие швы не нужны; «один процесс, точка» — правильный финал такого
раунда, а не пропуск. Ответ засчитывается, когда участник показал, что ни один из четырёх
симптомов не срабатывает.

**Граница предмета.** Агенты, их роли и мультиагентный паттерн в кейсе даны — их не
пересматриваем (выбор мультиагентного паттерна — предмет тренажёра multi-agent-case-drill). Здесь решается
другое: где проходят границы процессов и сервисов и что течёт через них. Twist'ы тоже никогда не
требуют пересобирать агентов — только швы.

## 2. Разложение по осям (диагностический каркас)

Если гейт пройден (симптом назван), каждый открытый шов раскладывается по осям — из фактов о
продукте выводятся **требования** к решению:

| Вопрос оси | Что участник выводит из фактов о продукте |
|---|---|
| **Ждать или в фон?** | есть ли главному агенту и пользователю чем полезным заняться, пока операция идёт; следующий шаг зависит от результата и делать нечего → синхронный вызов честнее |
| **Где исполнять?** | рядом в том же процессе (нулевая задержка, одна точка эксплуатации — правильный старт по умолчанию) или отдельным сервисом за сетью (только под независимый масштаб или независимое владение) |
| **Кто по обе стороны шва?** | обе стороны свои → внутренний контракт стека; чужой вендор или фреймворк → межвендорный стандарт; чужая сторона — простая возможность «вход → выход» → может, это вообще инструмент |
| **Как узнать результат?** | что есть у получателя: ничего → поллинг; доступный извне приёмник → вебхук; живой интерфейс с соединением → стриминг; пользователь уходит и возвращается → нужен rejoin |
| **Что должен показывать интерфейс?** | финального текста хватает / нужно видеть процесс (информативный слой) / состав экрана известен только в рантайме (генеративный, каталог) |
| **Переживёт ли фон рестарт — и должен ли?** | работа короткая и дешёвая → перезапуск честен; долгая или дорогая → чекпоинты во внешний стор (durable execution) обязательны |
| **Насколько это надолго?** | прототип к демо → скучное, стабильное и быстрое, молодой стандарт может подождать; продукт надолго с чужими интеграциями → консервативный выбор, зрелость стандарта — часть цены |

Ключ: **протокол — производная от ответов на оси**. Хороший ответ участника сначала называет
требования, потом протокол; плохой — сразу «возьмём A2A», а оси подгоняет под ответ.

## 3. Карманный алгоритм выбора

Он не заменяет думание, но правильно ставит первые вопросы:

1. **Симптомов нет?** → один процесс, точка (гейт из раздела 1).
2. **По каждому симптому — свой шов, по одному за раз:**
   - Долгая операция блокирует диалог + есть чем заняться → **фоновая джоба**. Исполнение —
     co-deployed, пока не нужны независимый масштаб или владение. Доставка — по возможностям
     получателя (поллинг / вебхук / стриминг). Работа долгая или дорогая → чекпоинты во внешний
     стор.
   - Чужой жизненный цикл части системы или независимый масштаб → **агент как сервис**;
     потребителям — discovery (перечисление + схемы).
   - Внешний потребитель — чужой агент другого вендора → **A2A** (визитка, задача). Чужая
     сторона — простая возможность «вход → выход» → взвесь **MCP-обёртку**. Обе стороны свои →
     **внутренний контракт**, межвендорный стандарт не нужен.
   - Интерфейс перерос текст → сначала **информативный слой** (стриминг состояния — свой фронт
     под своего агента; событийный протокол — если нужна переносимость клиентов). Состав экрана
     рождается в рантайме → **каталог компонентов**. Сырая вёрстка — почти никогда.
3. **Цена каждого открытого шва — часть ответа**, а не сноска: чем платишь и почему это
   окупается — включая зрелость выбранного стандарта: для прототипа честный ответ бывает «взять
   скучное и стабильное», для продукта надолго — явный шаг сверки диалектов в плане интеграции.

## 4. Пары-соседи, на которых чаще всего ошибаются

- **Синхронный вызов vs фоновая джоба.** Нечем заняться, пока работа идёт, → фон не даёт ничего,
  кроме сложности; sync — YAGNI, а не отсталость. И наоборот: диалог встал на минуты при живых
  пользователях → пора в фон.
- **Co-deployed vs отдельный сервис.** Фоновость ≠ удалённость — это две ортогональные оси.
  Выноси за сеть только за независимым масштабом или владением; иначе платишь сетью,
  аутентификацией и эксплуатацией впустую.
- **A2A vs MCP-обёртка.** Партнёрство над задачей (многоходовость, уточнения, долгие задачи,
  своя память чужого агента) → A2A; использование возможности (чёткий вход → выход, стейтлесс) →
  MCP. Заворачивание живого агента в тул урезает переговоры до одного вызова функции.
- **A2A vs внутренний контракт.** Межвендорный стандарт между двумя СВОИМИ сервисами — плата
  (диалекты, консервативность, совместимость) без выгоды. Стандарт — для чужих.
- **Поллинг vs вебхук vs стриминг.** Не «лучше/хуже», а «кто инициирует и чем платит»: у
  получателя нет ни адреса, ни соединения → поллинг; есть серверный приёмник → вебхук; живой
  интерфейс и нужен прогресс → стриминг, плюс rejoin, если пользователи уходят и возвращаются.
- **Стриминг состояния vs событийный протокол.** Оба — информативный UI, вёрстка у разработчика;
  разница только в контракте: свой фронт, намертво знающий своего агента (мощно, точно,
  одноразово), vs стандартные события (переносимо между бэкендами и клиентами).
- **Информативный vs генеративный UI.** «Показывать процесс» — ещё не повод отдавать агенту
  вёрстку; генеративный слой — только когда состав экрана реально рождается в рантайме.
- **Каталог vs сырая вёрстка.** Каталог — граница доверия и предсказуемость; сырая вёрстка — не
  «максимальная версия каталога», а редкий край спектра с другим уровнем требований к доверию.

## 5. Композиции и расстановка по типовым продуктам

Реальная система — почти всегда предложение из нескольких слов словаря. Проверяй, видит ли
участник связки, а не выбирает «одно блюдо»:

- **Классика зрелого продукта:** агент-сервис + фоновая джоба + вебхук между сервисами + стриминг
  в интерфейс. Три решения на трёх швах — не конкуренты, а слои одной системы.
- **Форма поверх стриминга.** Данные для формы едут фронту стримингом состояния, форму рисует
  каталог, ответ возвращается занятому агенту через enqueue. Информативный и генеративный слои
  работают вместе, а не вместо друг друга.
- **A2A наружу + внутренний контракт внутри.** Свои сервисы говорят на контракте стека, чужим
  выставлена визитка и стандартный эндпоинт. Не «один протокол на всё».
- **Sync там, где sync честен.** Даже в распределённой системе часть вызовов остаётся синхронной —
  фон только там, где ожиданию есть чем заняться.

Ориентиры по типовым продуктам (не догма):

- **Узкий сервис, операции на секунды, одна команда:** гейт не пройден → один процесс. Самый
  частый кейс «правильный ответ — не масштабировать».
- **Ассистент с проверками/отчётами на минуты при активных пользователях:** фоновая джоба
  co-deployed + статус в интерфейсе; за сеть не выносить, пока нет своих причин.
- **Платформа, чьих агентов зовут другие команды:** агент как сервис + discovery; потребителям с
  серверами — вебхуки.
- **Интеграция с агентом внешнего вендора:** A2A с явным шагом сверки диалектов; если чужая
  сторона — простая возможность, честно взвесить MCP-обёртку.
- **Продукт с опросами и формами под конкретный кейс:** информативный слой + каталог компонентов;
  генератор UI — отдельным вызовом, не в промпте основного агента.

Главное, что участник должен унести: **выбор выводится из симптомов и осей, а не из красоты
архитектуры**; тот же продукт при смене одного факта (операция стала часовой, пришёл чужой агент,
пользователи стали уходить со страницы) честно переезжает на другое решение — это инженерия, а не
непоследовательность.
