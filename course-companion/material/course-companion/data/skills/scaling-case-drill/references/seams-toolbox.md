## 1. Базовая рамка: карта швов

Агентная система растёт наружу через счётное число **швов** — мест, где взаимодействие пересекает
границу процесса, команды или вендора. У каждого шва свой класс решения; главная эвристика домена —
**протокол выбирается швом, а не модой**:

| Шов | Что передаётся | Класс решения |
|---|---|---|
| пользователь ↔ агент | состояние/события выполнения | API агент-сервиса + информативный UI |
| агент ↔ инструмент | вызов возможности: вход → выход | MCP |
| агент ↔ агент, обе стороны свои | фоновая джоба | внутренний контракт своего стека |
| агент ↔ агент, чужой вендор | задача как unit of work | A2A |
| агент ↔ динамический UI | описание интерфейса данными | декларативный (каталожный) UI |

Две ортогональные оси, на которых всё строится: **асинхронность** (ждать или в фон) и
**удалённость** (тот же процесс или другой сервис за сетью). Они комбинируются свободно: бывает
фоновая работа рядом в процессе и бывает синхронный вызов за сеть.

## 2. Классы решений — карточки

### Фоновая джоба (джоб-паттерн) — работа живёт дольше одного шага диалога

Асинхронная делегация всегда сводится к **job** — сущности с идентификатором. Минимально
достаточный набор операций: запустить (мгновенно получить id) · проверить статус · дослать
инструкцию · отменить · список задач. Жизненный цикл один на все реализации: принята → работает →
(ждёт ввода) → завершена / упала / отменена; «ждёт ввода» — рабочее состояние, не сбой.

- **Определяющее ограничение:** асинхронность имеет смысл, только когда главному агенту и
  пользователю **есть чем полезным заняться**, пока задача идёт. Если следующий шаг зависит от
  результата и делать больше нечего — фон не даёт ничего, кроме сложности; синхронный вызов
  честнее (это буквально «субагент как инструмент»: вызвал — получил — пошёл дальше).
- **Сильные стороны:** диалог не блокируется; несколько независимых задач параллельно;
  управляемость — статус, отмена, «дослать инструкцию» (по сути interrupt к собственной задаче).
- **Цена:** id надо тащить через диалог и помнить; результат сам не приходит — нужна доставка
  (триада ниже); второе обращение к занятому агенту — не edge case, а неизбежность
  (**double-texting**: enqueue / reject / interrupt / rollback; зрелые продукты комбинируют —
  enqueue-дефолт плюс interrupt по явному действию пользователя).
- **Durable execution:** фон, который долог или дорог, обязан переживать рестарт — чекпоинты во
  внешний стор, тот же класс персистентности, что у главного диалога. Ловушка не техническая, а
  статусная: фоновое интуитивно считают «второстепенным» и держат в памяти процесса — пока
  задача, считавшая три часа, не умрёт вместе с ним.

### Триада доставки результата — поллинг / вебхук / стриминг

Три ответа на вопрос «кто инициирует получение результата и чем за это платит». Повторяются в
любом асинхронном API — и стандартизованы в A2A в том же составе:

- **Поллинг** — получатель сам периодически спрашивает «готово?». Просто, получателю ничего не
  нужно (ни адреса, ни соединения); цена — задержка до следующего опроса и пустые запросы.
- **Вебхук** — исполнитель сам стучится HTTP-запросом на заранее заданный адрес. Опрашивать не
  надо; цена — у получателя должен быть доступный извне эндпоинт и забота о его безопасности.
- **Стриминг** — долгоживущее соединение, по которому едут промежуточные события, а не только
  финал. Живой прогресс; цена — соединение надо держать. Зрелая реализация умеет **rejoin** —
  переподключиться к уже идущей задаче: «я перестал смотреть» и «я прошу остановиться» — два
  разных действия, интерфейс обязан их различать.

### Агент как сервис — вынос за HTTP как качественный сдвиг

Не «тот же код, но по сети», а пять сдвигов разом: собственный жизненный цикл · версии
конфигурации (промпт + модель + тулы) без передеплоя кода · множество потребителей → нужен
контракт · состояние обязано переехать во внешний стор (инстансов несколько, любой может упасть) ·
приём запроса отделяется от исполнения (очередь + воркеры). Три роли любого агент-сервиса:
**конфигурация агента** · **диалог-контейнер** (персистентная память разговора) · **запуск**
(статус, поток событий, пауза, финал).

- **От классического микросервиса отличается по трём осям:** долгоживущее, дорогое,
  недетерминированное исполнение — диалог с накопленным контекстом является сущностью первого
  класса самого API; пауза на человека — часть контракта, а не исключение; интерфейс
  семантический, а не байт-точный.
- **Discovery внутри своей экосистемы:** операция перечисления доступных агентов + операция
  получения схем (вход/выход/состояние). Это НЕ то же, что межвендорная «визитка» для чужих, —
  та же задача на другом уровне доверия.
- **Цена:** stateless-инстансы + внешний стор = новая точка отказа; восстановление после падения
  воркера — минуты, не миллисекунды; multi-tenancy и авторизация — новые слои; чекпоинтинг на
  каждом значимом шаге стоит производительности.
- **Минимальный контракт** обозрим: считанные эндпоинты (создать диалог, запустить, статус,
  состояние, отменить) — вещь, которая помещается в голове, каким бы сложным ни был агент внутри.

### A2A — межвендорный шов агент↔агент

Решает N×M-проблему интеграций для отношения «агент↔агент» — тот же ход, что MCP сделал для
инструментов. Знакомство начинается с **agent card** («визитки»: что агент умеет, как с ним
говорить, как аутентифицироваться) на стандартном well-known-пути домена. Единица работы —
**задача** со стандартным жизненным циклом (тем же, что у джобы); завершённая задача иммутабельна —
уточнение или продолжение = **новая задача в том же контексте разговора**. Принцип **opaque
execution**: агенты сотрудничают, не раскрывая внутренностей, — чужой агент для тебя чёрный ящик.

- **Определяющее ограничение / граница с MCP:** *A2A — агенты партнёрятся над задачами; MCP —
  агенты используют возможности.* Чужая сторона проста и стейтлесс («вход → выход») → возможно,
  хватит MCP-обёртки; нужны многоходовость, уточнения посреди работы, долгие задачи → A2A.
  Заворачивание живого агента в тул урезает его автономность до «спросил-ответил».
- **Доставка результата задачи** — та же триада: поллинг / push-уведомления / стриминг.
- **Цена:** молодой стандарт — breaking-релизы, расхождения диалектов между реализациями, режимы
  совместимости. Сверку диалектов закладывай в план интеграции явным шагом.

### Спектр UI — кто владеет вёрсткой

Четыре позиции одной оси:

1. **Стриминг состояния** — фронт типизированно читает состояние своего агента (диалог, ключи
   стейта, статусы вызовов инструментов) и сам решает, как рисовать. Максимум контроля — и
   максимум связанности: чужой клиент, не знающий схему агента, не заработает.
2. **Событийный протокол** — поток стандартных событий («вызван инструмент», «дельта состояния»,
   «запуск завершён»); вёрстка по-прежнему на фронте, но контракт — форма события: любой бэкенд
   протокола совместим с любым его клиентом.
3. **Компоненты из каталога** (декларативный UI) — агент присылает описание интерфейса данными;
   фронт знает только каталог допустимых компонентов (граница доверия) и свою дизайн-систему.
   Состав экрана рождается в рантайме.
4. **Сырая вёрстка от модели** — агент пишет разметку напрямую. Максимум гибкости и максимум
   цены: ошибки, токены, доверие к сгенерированному коду. Оправдано редко.

Позиции 1–2 — **информативный UI** (показать процесс; вся вёрстка у разработчика), 3–4 —
**генеративный** (агент влияет на вёрстку). Асинхронный интерфейс обязан уметь три вещи
независимо от позиции: показывать фоновую работу как сущность первого класса · принимать ввод,
пока агент занят (enqueue глазами пользователя) · rejoin к бегущей задаче.

Тонкость генеративного UI: описание интерфейса обычно генерирует **не основной агент**, а
отдельный генератор со своим системным промптом (схемы протокола + каталог — порядка десятка
тысяч токенов), смотрящий на состояние агента; ответ пользователя возвращается основному агенту
обычным сообщением в диалог.

## 3. Сводные таблицы

Триада доставки:

| Способ | Кто инициирует | Что нужно получателю | Цена |
|---|---|---|---|
| Поллинг | получатель | ничего | задержка + пустые запросы |
| Вебхук | исполнитель | доступный извне эндпоинт | безопасность приёмника |
| Стриминг | канал держат вместе | живое соединение | держать соединение; уметь rejoin |

Спектр UI по трём осям:

| Позиция | Контроль над видом | Связанность с агентом | Что умеет чужой клиент |
|---|---|---|---|
| Стриминг состояния | полный | максимальная (схема агента) | ничего |
| Событийный протокол | полный | форма событий | любой клиент протокола |
| Каталог компонентов | по типам компонентов | минимальная | отрендерит незнакомого агента |
| Сырая вёрстка | почти никакого | — | вопрос доверия, не совместимости |

Жизненный цикл задачи — один словарь на внутреннюю джобу, запуск агент-сервиса и A2A-задачу:
**принята → работает → (ждёт ввода) → завершена / упала / отменена**.

## 4. Где что живёт (для опционального бонус-вопроса «чем собирать»)

- **Агент-сервер из коробки** (промышленные платформы типа LangGraph Agent Server): диалоги и
  запуски с очередью и воркерами; чекпоинты во внешний стор; стриминг событий; вебхуки; стратегии
  double-texting параметром запуска; discovery (перечисление агентов + схемы + автодоки);
  A2A-эндпоинт и визитка автоматически. Превращение агента в сервис — декларация в конфиге, а не
  переписывание кода.
- **Руками собирается:** приёмник вебхука (десяток строк на любом веб-фреймворке); фронт —
  компоненты под стриминг состояния или рендерер каталога; генератор UI со своим промптом; свой
  REST-контракт, если решил жить без стандарта, — вместе с его документацией и эволюцией.

Суть ответа, который стоит услышать: не «платформа X лучше», а понимание, что́ достаётся готовым
примитивом, а что́ — твой код и твоя эксплуатация.
