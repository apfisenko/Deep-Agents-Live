## Аспект 1: Субагенты (`subagents`)

**Что проверять:**

- **Изоляция:** каждый субагент решает одну задачу — не универсальный «делай всё». Ищи отдельные файлы/классы для `homework_checker`, `course_qa` и т.д.
- **Два подхода:** должны быть реализованы оба:
  - *CompiledSubAgent* — субагент как `Runnable` / граф (например, `homework_checker` с `StateGraph` или `RunnableLambda`)
  - *DeclarativeSubAgent* — субагент как dict-спека `{"name": ..., "tools": ..., "prompt": ...}`
- **Нет прямого общения с пользователем:** субагент не вызывает `input()` и не пишет напрямую в консоль — только возвращает результат оркестратору.

**Признаки хорошей реализации:**
- `homework_checker.py` — отдельный граф-адаптер, принимает рубрику и workspace, возвращает `AIMessage`
- `course_qa.py` — dict-спека с тулами `list_kb_docs` / `read_kb_doc`
- Субагенты не импортируют друг друга

**Типичные проблемы:**
- Один «god-agent» вместо разделённых субагентов
- DeclarativeSubAgent не оформлен как dict — просто другой `AgentExecutor`
- Субагент бросает исключение вместо возврата ошибки в `AIMessage`

## Аспект 2: Handoffs (передача управления)

**Что проверять:**

- **Механизм:** режимы переключаются без пересоздания агента. Ищи `middleware.py` или аналог с `select_prompt` / `filter_tools`.
- **Сохранение истории:** при переходе qa→homework→review сообщения не сбрасываются. Проверь что `messages` в state не очищаются при смене режима.
- **Явный Command:** переход инициируется инструментом (`switch_to_homework`, `complete_homework`, `return_to_qa`) — не `if/else` в основном потоке.

**Признаки хорошей реализации:**
- `mode_tools.py` — отдельный файл с тул-функциями переходов
- `build_modes_middleware()` возвращает функцию, оборачивающую агента
- Тесты покрывают переходы qa→homework и homework→review

**Типичные проблемы:**
- Нет middleware — режим определяется внутри основного агента через `if mode == "homework"`
- Переключение ломает историю (новый `messages=[]`)
- `resubmit_homework` не реализован или не протестирован

## Аспект 3: Router (классификатор интента)

**Что проверять:**

- **Отделён от агента:** Router — отдельный узел/функция, не встроен в companion. Ищи `router.py` с собственным классом или функцией.
- **Structured output:** классификация через Pydantic-модель (`Intent`) с `Literal["qa", "homework", "stay"]` — не regex по тексту.
- **Sticky + fail-safe:** 
  - *sticky* — если режим уже `homework`, Router видит это и может вернуть `stay`
  - *fail-safe* — при ошибке LLM возвращается `stay`, не падает с exception

**Признаки хорошей реализации:**
- `intent.py` — Pydantic `Intent` с полем `intent: Literal[...]`
- Router видит последние N сообщений + текущий `mode` из state
- Тест с mock LLM, бросающим исключение → проверяет что результат `stay`

**Типичные проблемы:**
- Router использует `response.content.startswith("homework")` вместо structured output
- Нет sticky-логики — Router игнорирует текущий режим
- При сбое LLM падает `KeyError` или `ValidationError` вместо `stay`

## Аспект 4: Skills (подключаемая экспертиза)

**Что проверять:**

- **Декларативная рубрика:** рубрика = YAML-файл + SKILL.md. Не хардкод в Python-коде.
- **Без правки кода:** подключение новой рубрики не требует изменения агента — только добавить директорию в `src/skills/`.
- **Рубрика для dogfooding:** существует `src/skills/multi-agent/rubric.yaml` с пятью аспектами — значит система способна проверять сама себя.

**Признаки хорошей реализации:**
- `resolver.py` — `resolve_rubric(topic)` находит рубрику по `match_keywords` без обращения к базе данных
- `rubric.yaml` содержит `match_keywords` для нечёткого матчинга
- `SKILL.md` содержит инструкции для reviewer-субагентов (не просто название аспектов)

**Типичные проблемы:**
- Рубрика захардкожена в `homework_checker.py`
- `resolve_rubric` зависит от cwd (используется относительный путь)
- `SKILL.md` есть, но содержит только список критериев без инструкций «что именно искать»

## Аспект 5: Custom Workflow

**Что проверять:**

- **Явный StateGraph:** граф строится через `StateGraph(CourseCompanionState)` — не `AgentExecutor` или `create_react_agent` без кастомного графа.
- **Типизированный State:** `CourseCompanionState` — `TypedDict` или Pydantic BaseModel с явными полями (`messages`, `mode`, `hw_artifacts`).
- **Checkpointer:** для многоходового диалога подключён `InMemorySaver` или аналог. Без чекпоинтера сессия теряет контекст.

**Признаки хорошей реализации:**
- `graph.py` — `build_graph()` возвращает `CompiledStateGraph`
- `state.py` — отдельный файл только для `CourseCompanionState` и `HWArtifacts`
- CLI использует `app.stream(..., config={"configurable": {"thread_id": ...}})` — значит чекпоинтер работает

**Типичные проблемы:**
- Граф есть, но `thread_id` не передаётся → каждый запрос новая сессия
- `State` — просто `dict` без типизации
- Router и Companion — не узлы графа, а `if/else` в основном цикле
